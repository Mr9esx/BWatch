# BiliFetch

监听 UP 主更新，自动收藏视频与图文动态。React + TypeScript + HeroUI 前端，Go 后端，使用 yt-dlp 下载视频，使用 B 站动态接口发现图文内容。交互参考 [biliup](https://github.com/biliup/biliup)。

## 功能

- **订阅管理**：B 站 UID / 空间主页、YouTube 频道；独立检查间隔、画质、监听开关。
- **视频与动态**：B 站可分别监听视频、文字、图片及转发动态；YouTube 支持频道视频。
- **历史回补**：订阅卡片选择「拉取历史」，指定最多新增任务数量，0 为全部可访问历史。视频、图文分别选择，逐页保存游标，支持暂停、继续、取消及服务重启后续接，自动跳过已有任务。
- **内容数量**：订阅和下载列表分别展示视频、图文的全部与已拉取数量。B 站总量优先采用空间导航接口 `/x/space/navnum` 的 `video` / `opus` 字段（图文为平台 Opus 口径），不需要完整扫描历史；启用中的订阅由后台自动补齐和刷新总量，不受内容检查间隔影响，每位 UP 主缓存一小时，重启保留缓存，遵守暂停及风控冷却。接口缺少对应字段时回退到已扫描目录，未完整扫描则显示「≥ 已发现数量」。已拉取按现存任务的内容 ID 去重，包含未完成的下载及图文转发，不含首次监听跳过的旧内容。
- **首次内容策略**：每次添加时选择「仅监听后续更新」或「同时归档最近 10 条」，每种所选内容分别处理。
- **下载队列**：1–4 并发、进度、速度、暂停、继续、失败重试；重启后恢复未完成任务。
- **网络与限速**：HTTP / HTTPS / SOCKS5 代理统一用于监听和下载；视频、图文支持单任务最大下载速度，0 为不限速。
- **内容库**：采用左侧 UP 主列表、右侧归档内容的布局，默认选中最近归档的 UP 主，支持搜索 UP/UID 和查看全部内容，保留已移除订阅的本地归档；右侧支持类型筛选、标题/正文/路径搜索、排序、卡片/列表视图及每页 12 条分页。服务器保存路径可复制，悬停或聚焦查看全文。支持本地视频播放，图文图片点击放大、左右按钮及方向键切换，Esc 关闭大图返回预览。图文可下载 ZIP（正文、原图和元数据）；封面使用已下载的本地图片。
- **资源监控**：工作台每 3 秒刷新 CPU、内存、系统上下行速率和下载目录所在磁盘的容量、已用、可用空间，并显示最近的网络采样趋势。网速按活动非回环网卡合计，包含其他程序流量；虚拟网卡也在此口径内。Docker 中展示容器可见的系统指标和下载卷所在文件系统，不能据此推断容器 CPU / 内存配额。首次网络采样显示等待，单项采集失败明确标注不可用。
- **图文归档**：Markdown 正文、原图、JSON 元数据保存在同一目录。
- **运行日志**：保留最近 500 条，可筛选和导出。

## 本地启动

需要 **Go 1.24+、Node.js 22、Python 3.10+、yt-dlp 和 FFmpeg**。以 macOS 为例：

```sh
brew install go node@22 ffmpeg
python3 -m venv .tools/venv
.tools/venv/bin/pip install yt-dlp
export PATH="$PWD/.tools/venv/bin:$PATH"
make install
make build
make run
```

打开 [http://127.0.0.1:8090](http://127.0.0.1:8090)。首次进入是真实空工作区，点击「添加订阅」开始。

若 yt-dlp 不在 PATH，可以显式指定：

```sh
BILIFETCH_YTDLP="$PWD/.tools/venv/bin/yt-dlp" ./bin/bilifetch
```

开发时分别运行：

```sh
make dev-server
make dev-web
```

开发页面为 [http://127.0.0.1:5173](http://127.0.0.1:5173)，API 代理至 Go 服务。

## Docker

```sh
docker compose up -d --build
```

访问 [http://127.0.0.1:8090](http://127.0.0.1:8090)。镜像包含 yt-dlp 和 FFmpeg，使用 UID 10001 运行。状态、下载分别保存在持久化命名卷中。

导出已下载文件：

```sh
docker compose cp bilifetch:/app/downloads ./downloads-backup
```

如需绑定 NAS 或本机目录，将 compose 中的卷改为 `/你的目录:/app/downloads` 和 `/你的数据目录:/app/data`，并确保容器 UID 10001 可读写。默认只映射本机端口；本版面向单用户且不含账号登录，不要直接暴露到公网，远程使用应由带认证的反向代理提供访问。

## B 站扫码登录与访客会话

在「偏好设置」点击「扫码登录」，使用哔哩哔哩 App 扫码并在手机上确认。手机确认前不会保存登录态；成功后 Cookie 仅写入服务端数据目录中的 `bilibili-login-*.cookies.txt`，权限为 `0600`，供视频与图文共用。二维码约 3 分钟有效，可刷新。

未配置登录 Cookie 时，BiliFetch 会访问 B 站正常主页及访客初始化接口，保存平台实际下发的匿名访客 Cookie（按网络出口隔离缓存 24 小时）。这不等于登录，不提供超出访客权限的画质或内容。B 站监听统一使用桌面端动态接口发现原创视频投稿和图文，避免单独依赖易受 412 影响的 WBI 视频列表；视频实际下载仍使用 yt-dlp。同时兼容对象与数组两种模块结构。

在「偏好设置」设置网络代理，Go 与 yt-dlp 会使用相同出口；留空时使用启动环境变量 `BILIFETCH_PROXY`，未设置该变量则直连。当前机器已验证 `http://127.0.0.1:7897`。Docker 内的 `127.0.0.1` 指容器自身，请使用容器可访问的代理地址。变更网络后建议重新扫码。

检测到 412 / -352 等风控时，自动检查按 30 分钟、1 小时、2 小时递增退避，最多 6 小时；设置页和订阅卡片显示错误。手动检查可以立即重试，但不建议反复触发。扫码成功后会恢复 B 站检查调度。每次 yt-dlp 调用使用独立的临时 Cookie 副本，避免并发重写原始凭据。

### 手动提供 Cookie 文件

在「偏好设置」填写**服务端**可读取的 Netscape 格式 `cookies.txt` 路径。视频解析和 B 站动态共用此文件。Docker 中可复制到数据卷：

```sh
docker compose cp ./cookies.txt bilifetch:/app/data/cookies.txt
```

然后填写 `/app/data/cookies.txt`，确保文件归 UID 10001 所有且可写（yt-dlp 可能更新 Cookie）。只使用自己账号的 Cookie，不要将凭据提交到 Git。

## 配置

- `BILIFETCH_ADDR`：默认 `127.0.0.1:8090`。
- `BILIFETCH_DATA`：默认 `./data`，存储 `state.json`。
- `BILIFETCH_DOWNLOADS`：默认 `./downloads`。
- `BILIFETCH_WEB`：默认 `./web/dist`，前端生产文件。
- `BILIFETCH_PROXY`：默认网络代理（HTTP/HTTPS/SOCKS5 URL），设置页的代理优先；不自动继承 macOS 系统代理。
- `BILIFETCH_YTDLP`：默认 `yt-dlp`，可填绝对路径。
- `BILIFETCH_DEV_ORIGIN`：开发时允许的前端 Origin，`make dev-server` 自动设为 `http://127.0.0.1:5173`。

在「偏好设置 → 网络与限速」设置代理和单任务最大下载速度。代理支持 `http://`、`https://`、`socks5://`、`socks5h://`（可带用户名和密码）；留空时使用 `BILIFETCH_PROXY`，环境变量也为空时直连。限速单位为 MB/s（1 MB = 1,000,000 字节），0 表示不限速，支持 0.001–100000 MB/s。视频与图文均按每个任务限速，多个并发任务的总速度可能达到限速值乘以并发数。保存后对新启动或恢复的任务生效，正在下载的任务保持启动时配置。

B 站下载默认随机间隔 **1–3 分钟**，在偏好设置配置上下限，填相同值即固定间隔。该间隔限制相邻任务的**启动时间**，并发数（1–4）限制同时运行的任务数；视频和图文共用节奏。等待时间及风控冷却保存在本机，重启不会清空。新安装默认并发 1、最高可用画质；已有配置会保留。

历史列表每 15–30 秒读取一页；B 站待处理任务达到 50 条时停止历史翻页，队列有空位后继续。暂停历史只暂停发现过程，已入队任务仍按下载队列执行。接口出现分页游标异常时停止并显示错误，避免无限拉取。HTTP 412/429、-352 等风控会让所有 B 站列表请求和新下载进入至少 30 分钟的冷却，重复触发逐步延长至 6 小时；不会绕过验证码或权限限制。降低请求频率不能保证账号不会受到平台限制。

「偏好设置」中的检查间隔和画质用于**新订阅默认值**，已有订阅保持创建时设置；并发数即时影响后续任务，字幕、封面和 Cookie 设置用于后续下载。

下载文件布局：`downloads/<订阅ID>/<任务ID>/`。图文包含 `content.md`、`metadata.json` 和 `image-01.jpg` 等；视频包含视频文件、yt-dlp 元数据，以及按设置保存的封面与字幕。移除订阅或任务保留本地文件，避免误删；可从磁盘手动清理。

## 行为边界

- Go 服务必须持续运行才能检查更新；关闭网页不影响后台监听。
- 首次成功扫描建立基线。选择仅新内容时，添加后至首次成功扫描前发布的内容也会被视为已有内容；接口失败不会建立基线。
- B 站的视频投稿与图文日常检查最近 3 页动态；首次选择归档历史时继续翻页，直到每种所选内容取得 10 条或接口结束，最多 12 页。达到上限仍未取全时明确报错，不建立不完整基线。YouTube 检查最近 50 条视频。长时间停机或发布频率极高可能导致旧内容超出窗口；需要补齐时手动启动历史拉取；只能读取平台实际返回且当前账号有权访问的内容。
- 原创视频动态由视频监听处理，图文监听不重复下载视频；转发动态保存转发文字及接口返回的原文与图片。长专栏/Opus 以动态接口返回的正文或摘要为准，不递归抓取专栏详情。
- B 站动态接口属于非稳定公开接口，平台可能更改格式或要求 Cookie、返回 412/-352。页面和日志会显示错误，需检查登录状态、更新 yt-dlp 或稍后重试。
- 视频可用画质取决于平台与账号权限，画质按短边优先选择目标以内的最佳格式；若全部超过目标则选择最低可用格式，兼容 480×852 等竖屏视频。暂停终止下载子进程，继续后使用 yt-dlp `.part` 断点续传；合并阶段依赖 FFmpeg。暂停队列停止新任务调度及自动检查，正在下载的任务继续完成；单条任务可单独暂停。
- 图文支持 JPEG、PNG、WebP、GIF、AVIF，每条最多 30 张、每张最多 30MB；全部成功后才标记完成。
- 单进程原子 JSON 存储适合个人规模；勿让多个服务实例同时使用同一数据目录。高频进度只更新内存，任务状态落盘。建议定期备份数据与下载目录。

## 验证

```sh
make test
```

Go 测试覆盖首次基线、新内容去重、独立图文基线、暂停恢复、持久化失败回滚、URL 校验、API 同源校验、目录与符号链接边界、动态解析、真实子进程扫描至下载产物链路。外部 yt-dlp 子进程在测试中由可控程序替代，不需要平台账号或实际下载大文件。

前端构建执行 TypeScript 类型检查与 Vite 生产打包。

2026-10-18 本机联调已使用真实 B 站接口验证：扫码确认后登录状态为有效；同一订阅扫描发现视频与图文，后台队列自动下载成功。样本包括 14 分 33 秒横屏视频（约 64MB）、40 秒竖屏视频（480×852，含音轨）和两条含原图动态。图文 ZIP 的正文、原图及元数据完整性检查通过；重复扫描没有重复入队。该验证使用已有发布内容，不代表已等待并观察到下一次新投稿。实时联调凭据和下载产物不纳入源码。 后续历史回补联调新增了两条视频，均按账号返回的最高分辨率下载（2844×1600，含音轨），并实际观察到第二条任务按 1–3 分钟随机启动间隔等待；相邻任务未同时抢跑。
